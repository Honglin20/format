## 一、致命缺陷（阻塞实施）

### D1: `session/` ↔ `report/` 循环依赖

**位置**: ADR-008 §6 用户 API + §4 包结构

**问题**:
ADR-008 设计 `Study.run()` 返回 `StudyReport`（来自 `report/`），但 `report/` 需要导入 `SessionResult`（来自 `session/`）。两个包相互导入，Python 会报循环依赖错误。

ADR-008 的依赖图中 `session/` 和 `report/` 是平行层，没有说明这一矛盾如何解决。

**修复方向（选一）**:
- 方案 A：`Study.run()` 返回 `List[SessionResult]`，由调用方显式包装 `StudyReport(results)`
- 方案 B：`session/_study.py` 使用 lazy import（函数体内 import）避免模块级循环
- 方案 C：`StudyReport` 移入 `session/`（打破当前包结构设计）

推荐方案 A：用户 API 变为：
```python
results = study.run(calib_data, ...)
report = StudyReport(results)
report.save("results/")
```

### D2: `QuantConfig.to_op_config()` 对 `transform="prescale"` 无法完成翻译

**位置**: ADR-008 §2 QuantConfig + 实施计划 Task 1

**问题**:
`to_op_config()` 是纯方法（无副作用），但 `transform="prescale"` 需要创建 `PreScaleTransform(scale=<tensor>)`，而这个 tensor 要在 `Session.run()` 内部调用 `initialize_pre_scales()` 之后才存在。

`to_op_config()` 在 prescale 情形下无法完成翻译，因为所需的运行时张量还不存在。

**修复方向**:
- `to_op_config()` 对 `transform="prescale"` 输出 `IdentityTransform()` 占位，返回一个"不完整"的 `OpQuantConfig`
- `Session.run()` 分步驱动：
  1. `op_cfg = config.to_op_config()`（prescale 占位）
  2. `qs = QuantSession(model, op_cfg)`
  3. `qs.initialize_pre_scales(...)` → 实际替换 transform
  4. 后续 calibrate / analyze / evaluate

需要在 ADR-008 中明确记录这一两步翻译机制，避免 Task 1 实施者误以为 `to_op_config()` 是完整的一次性翻译。

## 二、高优先级问题（影响接口设计）

### H1: PerLayerOpt 功能在新设计中静默丢失

**位置**: `src/pipeline/format_study.py` L540–643；实施计划 Task 5

**问题**:
`run_format_study` 中有约 80 行的 PerLayerOpt 后处理：对每个 part 比较 None/Hadamard/SmoothQuant 三种 transform 的各层 QSNR，按层选最优 transform，组装 per-layer `OpQuantConfig`，再跑一次 session。

ADR-008 将 `Study` 定义为"纯 for 循环，不包含任何量化逻辑"，无法承载这一复杂后处理。实施计划中完全没有提及 PerLayerOpt 的去向。

**决策需求**: 明确该功能是否在重构后保留，若保留则需设计承载位置（Study 子类？独立工具函数？）。

---

### H2: Calibrator strategy 不在 `QuantConfig` 中

**位置**: ADR-008 §2 QuantConfig；`src/pipeline/runner.py` L104

**问题**:
- `ExperimentRunner` 硬编码 `MSEScaleStrategy()`
- `QuantSession.__init__` 默认 `MaxScaleStrategy()`
- `Session.__init__(calibrator=...)` 有 calibrator 参数，但它**不在** `QuantConfig` 字段中

这破坏了"QuantConfig 是用户唯一配置入口"的设计原则。用户仍需在构造 Session 时手动指定 calibrator，QuantConfig 的封装承诺不完整。

**修复方向**: 在 `QuantConfig` 中增加 `calibrator: str = "mse"` 字段（`"mse"` | `"max"` | `"percentile"` | `"kl"`），`Session.__init__` 从 `QuantConfig` 读取，不再暴露 calibrator 参数。

---

### H3: `transform` 字段在 weight vs activation 上语义歧义

**位置**: ADR-008 §2 QuantConfig；`src/pipeline/config.py:43–59`；`src/pipeline/format_study.py:134–150`

**问题**:
`QuantConfig` 注释写"transform 应用于 activation 角色"，但 `pipeline/config.py:resolve_config()` 对 weight 和 activation 使用**相同的** transform：
```python
weight_scheme = QuantScheme(format=fmt, granularity=granularity, transform=transform, ...)
act_scheme    = QuantScheme(format=act_fmt, granularity=granularity, transform=transform, ...)
```

而 SmoothQuant 是 activation-only 的（`_make_sq_op_cfg` 中 weight 用 `IdentityTransform`）。`to_op_config()` 对 `transform="smoothquant"` 的翻译需要特判，但文档中没有说明这一逻辑。

**修复方向**: 在 ADR-008 中明确记录：`to_op_config()` 对不同 transform 的 weight/act 分配规则：
- `"hadamard"` / `"prescale"` → weight 和 activation 都应用
- `"smoothquant"` → 只有 activation（input），weight 用 `IdentityTransform`
- `"none"` → 两者都是 `IdentityTransform`

## 三、结构问题（影响层级模型）

### S1: `report/_spec.py` 需要导入 `analysis.observers`

**位置**: ADR-008 §3 Output-Driven Observer 选择

**问题**:
`_OUTPUT_SPEC` 映射 output key → observer class。若 `_spec.py` 持有 `QSNRObserver`、`MSEObserver` 等 class 引用，`report/` 就依赖 `analysis/`，打破了 `report/` 是"纯输出层"的设计定位。

**修复方向**: `_spec.py` 只返回字符串 key（如 `"qsnr"`、`"mse"`），observer class 解析逻辑放在 `session/_session.py` 中（执行层），`report/` 完全不感知 observer 实现。

---

### S2: `outputs="all"` → 16 个 key 未定义

**位置**: ADR-008 §3；实施计划 Task 3

**问题**:
ADR-008 声称 `outputs="all"` 对应"全部 16 个 key"，但 `_OUTPUT_SPEC` 示例只展示了 5 个，没有给出完整列表。Task 3 实施时如果没有这份列表，`_spec.py` 的内容无从决定。

**需补充**: 在 ADR-008 或 Task 3 描述中给出完整的 16 个 output key 枚举，及其对应的 observer/needs_eval/needs_cost 映射。

## 四、现有代码缺陷（可随重构修复）

### C1: SmoothQuant 重复计算

**位置**: `src/pipeline/format_study.py` L398 + L582

`_make_smoothquant_transforms` 在 sq_cache 预处理时调用一次（L398），PerLayerOpt 后处理时对同一个 part 又调用一次（L582），没有复用。每次 SQ 标定都要完整跑一遍前向传播。重构时应将 sq_transforms 作为 part-level 缓存传递给 PerLayerOpt 逻辑。

### C2: fp32 model deepcopy 冗余

**位置**: `src/pipeline/runner.py` L136

```python
fp32_copy = copy.deepcopy(fp32_model)
fp32_metrics = eval_fn(fp32_copy, eval_data)
```

`QuantSession` 已经 `keep_fp32=True` 在内部保存了一份 fp32 model（`session.fp32_model`）。这里再做一次 deepcopy 是无效的性能浪费。重构后 `Session.run()` 应直接使用 `qs.fp32_model`。

### C3: `_resolve_transform` 接口不完整

**位置**: `src/pipeline/config.py:43–59`

只处理 `"none"` 和 `"hadamard"`，对 `"smoothquant"` 和 `"prescale"` 直接抛 `ValueError`。但这两者在 `study_config.py` 和 `format_study.py` 中被大量使用，只是绕过了 `resolve_config()` 走特殊路径。config 层接口不完整，对使用者有陷阱。

### C4: `_call_table` 吞掉 `TypeError`

**位置**: `src/pipeline/report.py:112`

```python
try:
    func(viz_dict, title=title, output_dir=output_dir, filename=filename)
except TypeError:
    func(viz_dict, output_dir)
```

为兼容旧版 viz 函数签名而写的 fallback 会静默吞掉合法的 TypeError（如 viz 函数内部参数类型错误），使调试困难。重构时应统一 viz 函数签名，删除此 fallback。

### C5: `extract_metric_per_layer` 返回类型假设脆弱

**位置**: `src/pipeline/runner.py:40`

```python
df = report.to_dataframe()
if isinstance(df, list):  # 手工鸭子类型检测
    ...
else:
    grouped = df.groupby("layer")[metric].mean()  # 隐式假设 pandas DataFrame
```

若 `Report.to_dataframe()` 的返回类型改变，这里不会抛出明确错误，而是产生错误结果。

## 五、概念一致性问题（低优先级）

### P1: `lsq_steps: int = 0` 与 ADR-006 存在矛盾

ADR-008 说"LSQ 是 transform 的使用模式，不是独立开关"，但 `lsq_steps: int = 0` 从用户视角依然是一个独立的"LSQ 开关"。ADR-006 明确拒绝"独立 lsq 开关"，两文档间存在表述矛盾。形式上通过 "只在 `transform='prescale'` + `lsq_steps > 0` 时生效" 约束来消解，但这是组合约束不是单字段语义，应在 ADR 中明确记录这一设计决策。

### P2: `prescale_granularity` vs `a_granularity` 双粒度困惑

`QuantConfig` 同时有 `a_granularity`（activation 量化粒度）和 `prescale_granularity`（prescale transform 粒度）。两者的关系没有明确文档说明：大多数场景下应该相同，但设计允许不同，行为将难以推理。
